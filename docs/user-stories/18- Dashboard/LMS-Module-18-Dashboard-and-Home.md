# Module 18 — Dashboard & Home

## User Story — Dashboard & Home

### Epic
LMS Operations, Monitoring & Business Overview

### Feature
Role-Based Home Dashboard, KPI Summary, Alerts, Quick Actions and Operational Drill-Down

### User Story
As an authorized LMS user  
I want to see a role- and scope-specific summary of the most important operational information when I enter the system  
So that I can understand the current business position, identify items requiring action and navigate quickly to the relevant workflow.

As a Branch-level user  
I want to see only the information belonging to my authorized branch scope  
So that branch data remains isolated and the dashboard reflects the operations I am responsible for.

---

## Rules & Business Constraints

1. The Dashboard is a read and navigation layer; it must not become a second source of truth for loans, collections, accounting, recovery, reports or maintenance.
2. Every dashboard query is scoped by `organization_id`.
3. Branch-scoped users are additionally restricted by `branch_id`.
4. A Branch Admin or Branch-level user must not see another branch's loans, customers, collections, overdue cases, cash position or employee metrics.
5. Organization-level users may view multiple branches only when their permissions explicitly allow that scope.
6. Dashboard widgets are permission-controlled; a user sees only widgets for data they are authorized to view.
7. Permission checks must be enforced server-side. Hiding a widget in the UI is not sufficient authorization.
8. Dashboard counts and monetary values must be derived from authoritative module data.
9. Money is always represented as integer paise in storage and calculations. Dashboard presentation may format the value for display, but must not use floating-point arithmetic as the source of truth.
10. Dashboard totals must not create, edit or adjust money movements.
11. Any money movement shown through dashboard drill-down remains governed by the owning module and its accounting rules.
12. Every authoritative money movement posts double-entry lines that sum to zero. The Dashboard does not post those entries itself.
13. Payment posting remains idempotent on an `Idempotency-Key`; Dashboard quick navigation must not bypass the owning payment workflow.
14. Part-payment appropriation remains penalty → interest → principal → fees.
15. EMI due dates displayed by the Dashboard are DATE-only and follow Asia/Kolkata business-date semantics.
16. The Dashboard must use the authoritative business date where business-day-based metrics are calculated.
17. Active, overdue, closed and other loan counts must use the authoritative loan lifecycle states.
18. Dashboard overdue information must be derived from the Overdue & Recovery module and must not independently apply penalties.
19. Dashboard penalty values are display-only summaries of authoritative overdue/ledger information.
20. Collection amounts must come from posted or otherwise authoritative collection records according to the selected metric definition.
21. Pending or failed transactions must not be shown as successfully collected.
22. Reversed transactions must be reflected according to the authoritative transaction and accounting state.
23. Cash widgets must reconcile to the authoritative branch cash/day-closing data and must not maintain a separate dashboard balance.
24. Receipt numbers are not generated by the Dashboard. Receipt numbering remains governed by the collection and field collection workflows, including gapless branch/agent and offline requirements.
25. Quick Actions only navigate to or initiate an authorized workflow; they must not bypass mandatory validation, approval, idempotency, branch scoping or audit controls.
26. A Dashboard quick action must not be shown if the user lacks permission for the destination action.
27. Alerts are informational or actionable pointers; resolving an alert must occur through the owning workflow unless an explicit action is supported.
28. Clicking an alert must open only data the user is authorized to access.
29. No dashboard widget may expose customer PII beyond the permissions and masking rules defined by the owning module.
30. A customer or loan drill-down must re-evaluate permission and organization/branch scope on the destination request.
31. Dashboard data freshness must be identifiable where asynchronous, cached or background-computed data is used.
32. Cached data must not be presented as a newly posted transaction if the source has not yet refreshed.
33. Failure to load one widget must not incorrectly fail the entire Dashboard where independent widget loading is supported.
34. A failed widget must show a controlled error state without fabricating zero values.
35. A genuine zero value must be distinguishable from an unavailable or failed data source.
36. No-data is a valid state and must not be treated as a system error.
37. Date filters and dashboard periods must validate against supported ranges.
38. A branch-level user cannot manipulate request parameters to obtain another branch's dashboard.
39. Dashboard configuration or personalization must not expand a user's authorization scope.
40. If user-specific widget layout preferences are supported, those preferences affect presentation only, not data access.
41. Dashboard data export is governed by the Reports & Analytics module and its permissions; the Dashboard must not bypass report export permissions.
42. Large analytical calculations should use the appropriate reporting/background-job path rather than blocking the home screen indefinitely.
43. Dashboard metrics that require expensive computation may use precomputed or cached aggregates, provided the source, scope and freshness are controlled.
44. Financial and operational corrections cannot be made by directly editing a Dashboard number.
45. Ledger corrections remain reversal entries, never edits or deletes.
46. Inactive records must behave according to the owning module: inactive master data cannot be used for new transactions, while historical records remain available where authorized.
47. Deletion of referenced source records is governed by the owning module and must not be enabled from the Dashboard.
48. Dashboard widgets must remain auditable where the underlying action is security-sensitive or operationally significant.
49. Access to the Dashboard and permission-denied attempts for protected drill-downs must follow the system audit policy.
50. All actions are audit logged.

## Background

Given the user is logged into the system  
And the user's organization and branch scope are resolved from the authenticated session  
And the user's effective permissions have been loaded  
And the Dashboard retrieves summary data only from authoritative LMS modules  
And the current business date follows Asia/Kolkata semantics  
And the user is authorized to view the Dashboard

The Dashboard is the default operational entry point and provides a consolidated view of relevant information from:

- Organizations & Branches
- Customers
- Loan Applications
- Approved and Active Loans
- Repayment Schedule
- EMI Collection
- Field Collection & Cash Reconciliation
- Overdue & Recovery
- Accounting & Ledger
- Reports & Analytics
- Notifications
- Settings, Audit & Maintenance

The Dashboard itself does not own or replace those records.

# Gherkin Scenarios

## Dashboard Access and List

### Scenario 1: Authorized user opens Dashboard

Given the user has Dashboard View permission  
And the user's organization and branch scope are resolved  
When the user opens the Dashboard  
Then the system loads only authorized widgets  
And all returned data is restricted to the user's authorized organization and branch scope.

### Scenario 2: User sees role-appropriate widgets

Given different users have different report, collection, approval and accounting permissions  
When each user opens the Dashboard  
Then each user sees only the widgets permitted by their effective permissions  
And restricted widget data is not returned to unauthorized users.

### Scenario 3: View Dashboard summary

Given authoritative LMS data exists for the selected scope  
When the Dashboard loads successfully  
Then the system displays the applicable loan, collection, overdue and operational summary  
And each metric is derived from its authoritative source module.

---

## Mandatory Field Validation

### Scenario Outline: Dashboard filter validation

Given the user has permission to view the Dashboard  
When the user submits a custom filter without <field>  
Then the system shows "<message>"  
And the invalid filter is not applied

Examples:

| field | message |
|---|---|
| Period Start Date | Period Start Date is required |
| Period End Date | Period End Date is required |
| Branch Scope | Branch Scope is required |
| Business Date | Business Date is required for this view |

---

## Date and Scope Filtering

### Scenario 4: Filter Dashboard by supported period

Given the user is viewing the Dashboard  
When the user selects Today, This Week, This Month or a valid Custom Date Range  
Then the Dashboard recalculates only the widgets that support the selected period  
And irrelevant widget filters are not applied.

### Scenario 5: Reject invalid date range

Given the user selects a custom date range  
When the Period End Date is before the Period Start Date  
Then the system rejects the filter  
And the previous valid Dashboard state remains available.

### Scenario 6: Organization-level user switches to an authorized branch

Given the user has permission to view multiple branches  
When the user selects an authorized branch  
Then the Dashboard reloads data for that branch  
And the displayed metrics do not combine unauthorized branches.

### Scenario 7: Branch Admin cannot switch to another branch

Given the Branch Admin belongs only to Branch A  
When the Branch Admin attempts to select Branch B through the UI or request parameters  
Then the system denies the unauthorized scope  
And Branch B data is not returned.

---

## Permission Denial

### Scenario 8: Wrong role attempts to access Dashboard

Given the user does not have Dashboard View permission  
When the user requests the Dashboard  
Then the system denies access  
And no Dashboard metrics are returned.

### Scenario 9: User cannot access protected widget drill-down

Given the user can view a high-level summary widget  
But does not have permission to view the underlying detailed records  
When the user selects the drill-down action  
Then the destination access check is enforced  
And restricted records are not exposed.

### Scenario 10: Quick Action is denied without destination permission

Given the user lacks permission to create a loan application  
When the user attempts to access the New Loan Application Quick Action directly  
Then the system denies the destination action  
And no application is created.

### Scenario 12: Drill down from overdue loan count

## Collection Summary

Given posted collection records exist for the current Asia/Kolkata business date  
When the Collection Summary widget loads  
Then the system displays the applicable Today's Due Amount and Today's Collected Amount

Given a collection attempt is pending, failed or rejected  
When the Dashboard computes Today's Collected Amount  
Then only authoritative successful/posted collection records are included according to the metric definition  
And failed or pending attempts are not counted as collected.

### Scenario 16: Dashboard drill-down preserves payment idempotency

Given the user opens a Collect EMI Quick Action from the Dashboard  
When the user submits a payment in the destination workflow  
Then the payment workflow requires its Idempotency-Key  
And the Dashboard does not create a duplicate payment posting.

### Scenario 17: Part-payment summary follows authoritative appropriation

Given a posted part-payment exists  
When collection details are displayed through Dashboard drill-down  
Then the underlying allocation follows penalty → interest → principal → fees  
And the Dashboard does not recalculate or override that allocation.

## Widget Failure and No-Data Behaviour

### Scenario 35: No data is a valid Dashboard state

Given no authoritative records match the selected filters  
When a widget completes successfully with an empty result  
Then the widget displays a clear No Data state  
And the selected filters remain available for modification.

### Scenario 36: Widget load failure does not fabricate zero

Given an individual Dashboard data source fails  
When the widget cannot retrieve its result  
Then the widget displays a controlled Failed or Unavailable state  
And the system does not replace the failure with a zero value.

### Scenario 37: Retry failed widget

Given a Dashboard widget failed due to a retryable error  
When the user selects Retry  
Then the system reloads only the applicable widget where supported  
And the retry remains within the user's authorized scope.

### Scenario 38: Stale cached metric is identified

Given a metric is temporarily served from an older valid snapshot  
When the Dashboard displays the metric  
Then the freshness state or last-updated information is available according to UI policy  
And the stale value is not presented as guaranteed live data.

## Active / Inactive and Deletion Behaviour

### Scenario 39: Historical inactive branch data remains viewable when authorized

Given a branch is inactive for new operations  
And historical records exist for that branch  
When an authorized organization-level user views historical Dashboard data  
Then historical metrics may be shown according to retention and reporting permissions  
And the inactive branch cannot be used for new transactions.

### Scenario 40: Dashboard does not delete referenced source records

Given a customer, loan, branch or configuration record is referenced downstream  
When a user views the record through a Dashboard drill-down  
Then the Dashboard provides no direct delete operation that bypasses the owning module  
And deletion remains blocked where the source record is referenced.

### Scenario 41: Deactivated source affects new transactions

Given a source configuration or master record has been deactivated  
When the Dashboard Quick Action leads to a new transaction requiring that source  
Then the destination workflow prevents use of the inactive record  
And historical Dashboard metrics remain preserved where authorized.

## Offline and Sync Conflict

### Scenario 42: Offline field activity is not immediately treated as synchronized Dashboard data

Given a Field Employee records a supported offline collection activity  
When the device has not yet synchronized successfully  
Then the central Dashboard does not treat the activity as authoritative posted collection unless the architecture explicitly exposes pending sync metrics  
And posted collection totals remain based on authoritative server state.

### Scenario 43: Sync conflict does not duplicate Dashboard collection totals

Given an offline activity is synchronized and a conflict or duplicate submission is detected  
When the server resolves the activity through the authoritative workflow  
Then duplicate business postings are prevented  
And the Dashboard reflects only the final authoritative result.

### Scenario 44: Offline receipt integrity remains in owning workflow

Given an offline field collection uses branch/agent receipt numbering  
When the activity later synchronizes  
Then receipt uniqueness and gapless sequencing are governed by the Field Collection workflow  
And the Dashboard only displays the resulting authoritative receipt or collection state.

Given a user successfully accesses the Dashboard

### Scenario 46: Permission denial is audit logged

Given a user attempts to access an unauthorized branch, widget or protected drill-down  
When the system denies access  
Then the denial is audit logged  
And no unauthorized data is returned.

### Scenario 47: Quick Action execution is traceable

Given a user starts an authorized workflow from a Dashboard Quick Action

# Acceptance Criteria

- The Dashboard is available only to users with Dashboard View permission.
- Every Dashboard query is scoped by organization and applicable branch.
- A Branch Admin cannot see or infer another branch's records or aggregate metrics.
- Organization-level cross-branch visibility requires explicit permission.
- Widget visibility and data access are permission-controlled server-side.
- The Dashboard uses authoritative data from owning LMS modules.
- The Dashboard does not independently create or edit loans, collections, ledger entries, penalties, receipts or repayment schedules.
- Money is calculated from integer paise and never from floating-point source values.
- EMI due-date metrics use DATE-only semantics in Asia/Kolkata.
- Loan state summaries reflect authoritative lifecycle states.
- Pending or failed payments are not counted as successful collections.
- Dashboard navigation to payment workflows preserves Idempotency-Key requirements.
- Part-payment details preserve penalty → interest → principal → fees allocation.
- Overdue and penalty information is derived from the authoritative recovery workflow.
- Cash summaries reconcile to authoritative branch cash and reconciliation data.
- The Dashboard cannot directly edit or delete posted ledger entries.
- Financial corrections remain reversal/correction operations in the owning workflow.
- Authoritative money movement drill-down preserves double-entry integrity, with debit and credit totals summing to zero.
- Receipt numbering is not generated or repaired by the Dashboard.
- Quick Actions are shown only for authorized destination actions.
- Quick Actions do not bypass validation, approval, branch scope, idempotency or audit controls.
- Alerts point to authoritative source workflows.
- Clicking an alert or metric performs a fresh authorization and scope check.
- No-data is shown as a valid state.
- Failed or unavailable data is not silently displayed as zero.
- Stale or cached data is identifiable according to freshness policy.
- Independent widget failure does not corrupt unrelated widget results.
- Offline field activity is not counted as authoritative posted collection until successfully processed according to the owning workflow.
- Sync conflicts and duplicate submissions do not duplicate Dashboard totals.
- Inactive records cannot be used for new transactions through Dashboard navigation.
- Historical data remains available according to authorization, retention and owning-module rules.
- Deletion remains governed by the owning module and is blocked when referenced downstream.
- Dashboard exports remain governed by Reports & Analytics permissions.
- All relevant successful and failed actions, including protected access and permission denials, are audit logged.
- All actions are audit logged.
